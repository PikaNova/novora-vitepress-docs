# 12. 日常维护

维护分为源码更新、部署监控、数据库备份、账号审计和故障处理。建议设置固定周期，而不是只在出现问题时登录平台。

## 更新前原则

每次更新前先完成：

1. 阅读目标版本的 Release Notes 和升级说明；
2. 确认当前生产版本；
3. 备份 Neon 数据；
4. 记录当前 Vercel 成功部署；
5. 避开考试和上课高峰；
6. 准备回滚方案。

V2 对旧字段有一定兼容和按需补列能力，但不保证所有 V1 自定义业务数据自动迁移。跨大版本升级前必须单独验证。

## 第一步：判断项目使用哪种仓库

先在 Vercel **Settings → Git** 查看 Connected Git Repository。

| 仓库方式 | 更新前要做什么 |
| --- | --- |
| 直接连接官方 `PikaNova/Novora` 的 `main` | 确认目标提交已经进入官方 `main` |
| 一键部署创建的个人仓库或 Fork | 先在 GitHub 使用 **Sync fork → Update branch** 同步官方上游 |
| 含学校自定义代码的 Fork | 建立升级分支，合并上游，解决冲突并完成测试后再合入生产 `main` |

::: warning 一键部署更新不等于自动合并上游
Deploy Hook 只让 Vercel 重新拉取已连接仓库的目标分支。若个人 Fork 仍是旧代码，反复点击只会重新部署旧版本。
:::

## 第二步：备份并记录当前状态

1. 在 Novora “系统设置 → 版本与更新”记录当前版本。
2. 在 Vercel **Deployments** 记录当前 Ready 的生产 Deployment、提交号和时间。
3. 使用 Neon 分支、`pg_dump` 或学校既定方案备份数据库。
4. 导出需要额外留存的大型考试和周测 JSON。
5. 选择没有考试、周测和课堂使用的维护窗口。

## 第三步：同步 GitHub 源码

使用 Fork 时，可以通过 GitHub 的 **Sync fork** 获取上游更新。若存在自己的代码修改，不要在生产前直接强制覆盖，应先在分支中合并并检查冲突。

零基础 Fork 更新步骤：

1. 登录 GitHub，打开自己名下的 Novora 仓库。
2. 检查页面是否显示 **This branch is behind PikaNova/Novora**。
3. 点击 **Sync fork**。
4. 点击 **Update branch**。
5. 等待同步完成，确认生产分支仍为 `main`。
6. 打开最新提交，确认版本文件和 Release Notes 对应目标版本。

如果 GitHub 提示冲突，不要点击丢弃自定义提交。应先建立测试分支处理冲突，或联系维护人员。合并到 Vercel 连接的生产分支后，Git 集成可能已经自动开始新部署；不要同时连续点击 Deploy Hook。

## 第四步：在客户端检查更新

1. 使用有部署权限的超级管理员登录。
2. 打开 **系统设置 → 版本与更新**。
3. 点击 **检查更新**。
4. 核对当前版本、最新版本和更新说明。
5. 展开 **查看后续更新完整流程**，确认前置工作已完成。

如果客户端发现新版本，但 Fork 尚未同步，先返回 GitHub 同步源码，不要直接触发部署。

“检查更新”读取官方 GitHub Release；它只负责比较版本，不会下载代码、修改数据库或自动开始部署。

## 第五步：一键部署更新

已配置 `VERCEL_DEPLOY_HOOK_URL` 且当前账号拥有 `deployment.trigger` 权限时：

1. 点击 **一键部署更新**一次。
2. 页面提示已触发后不要重复点击。
3. 打开 Vercel 项目 **Deployments**。
4. 确认出现来源为 Deploy Hook 或目标 `main` 提交的新部署。
5. 打开构建详情，确认依赖安装、`npm run build` 和输出发布成功。
6. 等待 Production 状态变为 **Ready**。

如果同步 Fork 后，Vercel 的 Git 集成已经自动创建了目标提交的部署，直接观察这一条部署即可，不要再点击按钮创建重复任务。

若按钮不存在，回到[配置环境变量：创建 Deploy Hook](/guide/07-environment#创建-deploy-hook-正式部署必做)检查 Hook、Production 环境和 Redeploy。

重新部署不会自动修改 Neon 中已存在的管理员密码，也不会清空业务数据。

## 第六步：更新后验收

每次更新至少验证：

- 首页和自定义域名；
- `/api/time`；
- 管理员登录；
- 后台读取和保存；
- 当前班级考试大屏；
- PDF 下载；
- ClassIsland 同步（如启用）；
- 浏览器更新提示和缓存刷新。

同时在“系统设置 → 关于”确认当前版本已经变化。若仍显示旧版本：

1. 确认 Fork 的 `main` 确实包含新版本；
2. 确认 Vercel 新部署使用的是该提交；
3. 等待 Service Worker 更新提示并刷新；
4. 必要时关闭全部旧标签页后重新打开。

## 第七步：记录更新结果

记录更新时间、旧版本、新版本、Git 提交、Vercel Deployment、数据库备份位置、执行人和验收结果。学校多人维护时，这一步能避免重复部署和版本责任不清。

## 更新失败时回滚

若新部署出现严重问题：

1. 打开 Vercel 项目的 **Deployments**；
2. 找到更新前已验证成功的部署；
3. 使用平台当前提供的 Promote、Rollback 或重新部署功能恢复；
4. 验证主域名是否已指向旧版本；
5. 记录故障版本和影响。

::: warning 代码回滚不等于数据库回滚
如果新版本已经改变数据库数据，恢复旧前端代码不一定能恢复数据状态。数据库恢复必须基于更新前备份评估，不能盲目覆盖生产库。
:::

## 数据库备份和恢复

使用 PostgreSQL 官方工具导出：

```bash
pg_dump --dbname="生产连接串" --format=custom --no-owner --no-privileges --file=novora-YYYY-MM-DD.dump
```

恢复到一套新的空数据库进行演练：

```bash
pg_restore --dbname="测试数据库连接串" --no-owner --no-privileges novora-YYYY-MM-DD.dump
```

不要直接拿未验证的备份覆盖生产数据库。恢复演练应使用独立 Neon 项目或分支，并确认管理员登录、学校结构和考试数据完整。

## 数据维护和重置

系统设置支持整体或按模块清理大型考试、周测、学校结构、设备/插件和调度设置。登录用户不会随普通业务数据重置自动删除。

数据重置是高风险操作。执行前：

- 确认选择的模块；
- 导出或备份数据；
- 通知正在使用系统的人员；
- 避免多名管理员同时操作；
- 完成后重新验收设备绑定和调度。

## 查看日志

遇到 API 错误时：

1. 记录页面显示的请求 ID、时间和操作；
2. 打开 Vercel 项目的 Logs 或 Functions 日志；
3. 按请求 ID搜索；
4. 检查是认证、权限、数据库、GitHub API 还是外部网络错误；
5. 不要在公开反馈中粘贴完整环境变量。

超时或临时断线可以有限次数重试；认证失败、环境变量缺失和数据库结构问题应先修正根因。

## 账号维护

建议每月检查：

- 超级管理员数量；
- 停用账号；
- 年级和班级授权范围；
- 审计日志中的异常删除、重置或部署操作；
- 是否仍有人共享账号；
- 密码重置后旧会话是否失效。

## 域名维护

- 开启域名自动续费并检查付款方式；
- 不要删除 Vercel 要求的 DNS 记录；
- 更换 DNS 服务商前完整复制记录；
- 域名或证书异常时先查看 Vercel Domains 状态；
- 每学期至少用学校网络和移动网络复测。

## 推荐维护周期

| 周期 | 工作 |
| --- | --- |
| 每周 | 检查部署、数据库和关键页面是否正常 |
| 每月 | 数据备份、账号权限和审计日志检查 |
| 每学期 | 校历、周次、节假日、年级班级和设备复核 |
| 每次更新前 | 读发布说明、备份、安排维护窗口 |
| 每次更新后 | 执行核心验收和记录版本 |

遇到问题时进入[故障排查](/appendix/a-troubleshooting)。需要修改代码时进入[本地开发](/appendix/b-local-development)。
